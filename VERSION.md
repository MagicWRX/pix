# VERSION — PIX.MOV Version Tracking

**Locked term: VERSION.** This document is the version system for PIX.MOV.
Lunk (auditor) maintains it; the Local agent follows it and records its
changes here; the Founder checks sync from it. It is also registered in
library.db (`library.documents.version`), which carries the same log with
commit IDs — the DB record is the shareable track.

## The system

1. **Directories are generations.** The Muse artifact's full source of
   record lives in the directory named for its generation: **`/v1/`** is the
   living tree of the 1.x line. A new directory (`/v2/`, …) appears only when
   the Founder declares a new generation; the old directory then freezes as
   that generation's archive. **Minor changes never create directories.**
2. **Numbers are the tracking.** The fine-grained version (format
   `1.00.00`) advances inside the generation directory. It is carried in
   three stamps that must always agree:
   - the **footer** of the app: `© 2026 PIX.MOV — All rights reserved. V<version>`
   - the **log** in this document (one row per version)
   - the **commit message** of the push that ships the change (`1.00.37 — …`)
   Git history is the per-version archive: any past version is retrievable
   by its commit. No folder-per-version, ever.
3. **Starting point.** The system starts fresh at **1.00.00** (2026-10-22).
   There is no target count and no ceiling — increments are open-ended.
4. **The honest-change rule.** The patch number bumps **only for an honest
   change** — a real modification to the source, shipped in the same pass:
   footer stamp updated, source pushed under the new version, log row added,
   DB record updated. No ceremonial bumps, no reserving numbers, no bump
   without the change it names. An increment missing any of the three
   stamps does not count as shipped.
5. **The sync check.** Founder / auditor / Local verify the chain at a
   glance: Muse artifact footer → this log's latest row → live site footer.
   Three stamps, one value. Any mismatch names the drift and its size.

## Who does what

- **Lunk (auditor):** issues increments with Muse-side changes, pushes the
  source into `/v1/`, maintains this document and the DB track, and audits
  the live site against the Muse artifact.
- **Local agent:** follows this document; never invents a version number;
  when a Local change ships to the live site that corresponds to a version,
  it records the row here (or requests the increment) in the same pass.
- **Founder:** declares new generations and approves the starting points.

## What a version directory holds — and what it never holds

Holds: 100% of the artifact's source files — `client/` (src, index.html,
configs), `server/` (src, contracts, configs), `drizzle/` migrations, and
root configs/docs (`package.json`, `bun.lock`, `space.json`, `AGENTS.md`, …).

Never holds: the live database (`app.db` — user data; travels only as
curated exports under `handoffs/data/`), the bundled asset payload
(`client/src/assets/`, ~1.3 GB of poster artwork — data; its manifest
`pixPosterManifest.ts` IS included), `node_modules`, build output, and
platform runtime directories.

**Declared transport exceptions** (push-channel limits, recorded — never
silent): `icon.jpg` is a binary and cannot travel the text snapshot channel.
`drizzle/0037_complete_2003_through_1896_year_decks.sql` (13,033,594 bytes,
SHA-256 `ccb2d47fe3405f43e50b5cec0f737f3683e0a5a0833433034ebd05cd8d210b0c`)
exceeds the channel's request limit and travels as 27 sequential parts in
`v1/drizzle/` (see its `PARTS.md`; reassembly verified byte-identical
against the hash above).
